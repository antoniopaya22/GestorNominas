# Crear Pull Request

Ejecuta el flujo completo para abrir un PR contra `development` usando `gh`.

## Reglas críticas

- ❌ NUNCA añadir:
  - "Co-authored-by: Claude"
  - "Generated by Claude"
  - cualquier referencia a Claude como autor
- El PR SIEMPRE debe parecer 100% humano
- NUNCA hacer push --force ni sobrescribir historia sin confirmación explícita

## Pasos

1. Verificar estado:
   - git status
   - git branch --show-current
   - Confirmar que no hay cambios sin commitear (si hay, avisar y detener)

2. Verificar tracking remoto:
   - git rev-parse --abbrev-ref --symbolic-full-name @{u} (si falla, se necesita `git push -u origin <branch>`)

3. Determinar rama base (por defecto `development`, salvo que el usuario indique otra)

4. Revisar todos los commits del branch respecto a la base:
   - git log <base>..HEAD --oneline
   - git diff <base>...HEAD --stat
   - git diff <base>...HEAD (para entender el contenido completo)

5. Extraer ID (ClickUp/Jira/etc) desde el nombre del branch

6. Push si es necesario:
   - git push -u origin <branch> (solo si no hay upstream o hay commits nuevos)

7. Generar título y cuerpo del PR:

Formato del título:
<type>(scope): descripción corta

Tipos: feat, fix, docs, style, refactor, perf, test, build, ci, chore

Reglas del título:
- Español
- Imperativo
- < 70 caracteres
- Sin punto final
- Incluir el ID del ticket si existe (ej. `CU-86cb61pzr`)
- NO mencionar IA ni Claude

Cuerpo del PR (usar heredoc, formato Markdown):

```
## Resumen
- Bullets del QUÉ cambió a alto nivel (componentes/módulos afectados y su rol)

## Motivación
Por qué se hizo el cambio (bug corregido, contexto del ticket/CU)

## Cambios por archivo
- `ruta/al/archivo.ext`: explicación concreta de qué se modificó ahí y por qué
- `ruta/al/otro_archivo.ext`: idem
  (repetir una entrada por cada archivo tocado; agrupar solo si son archivos
  triviales del mismo tipo, ej. varios `__init__.py` sin cambios de lógica)

## Impacto
Qué se rompía antes, qué se valida ahora, riesgos si aplica

## Plan de pruebas
- [ ] Checklist de verificación manual/automática relevante
```

Reglas del cuerpo:
- Español
- Basarse en TODOS los commits del branch, no solo el último
- La sección "Cambios por archivo" es OBLIGATORIA salvo que el PR toque un único archivo (en ese caso se puede omitir y explicar todo en "Resumen")
- Usar `git diff <base>...HEAD --name-status` para obtener la lista exacta de archivos y su estado (A/M/D/R)
- Cada entrada de archivo debe explicar el cambio real visto en el diff, no solo repetir el nombre del archivo
- Si un archivo fue renombrado o movido, indicarlo explícitamente (origen → destino)
- Si hubo merge/revert, indicarlo explícitamente
- Tan extenso como sea necesario para que un revisor sin contexto entienda el cambio
- NO mencionar IA ni Claude

8. Mostrar título y cuerpo propuestos, pedir confirmación antes de crear el PR

9. Crear el PR:
   - gh pr create --base <base> --title "<título>" --body "<cuerpo>"

10. Mostrar la URL del PR devuelta por `gh`
